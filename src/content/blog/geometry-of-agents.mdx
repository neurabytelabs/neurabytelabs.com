## Axioms Before APIs

Spinoza didn't write *Ethics* as philosophy. He wrote it as geometry. Definitions, axioms, propositions, proofs — the same structure you'd find in Euclid's *Elements*. Most philosophers found this bizarre. Most software architects should find it familiar.

When you design an autonomous agent, you face the same fundamental problem Spinoza faced: how do you build a system that behaves coherently without constant external instruction? Spinoza's answer was radical — derive everything from first principles, make the dependencies explicit, and let behavior emerge from structure.

That's not philosophy. That's architecture.

## Substance as Runtime

In Spinoza's system, there is exactly one substance — infinite, self-caused, containing everything. Every particular thing is a *mode* of that substance, a specific way the infinite expresses itself.

Translate this: your runtime environment is the substance. Every agent, every tool, every memory store is a mode — a particular configuration of the underlying computational substrate. They don't exist independently. They're expressions of the same system.

This isn't just analogy. When you build agents that share memory, share tools, share context windows — you're already building Spinozist architecture. You just didn't know it had a name.

## The Attribute Problem

Spinoza says substance has infinite attributes, but we can only perceive two: thought and extension (mind and body). This maps directly onto the dual nature of every agent system.

**Thought** is the agent's reasoning — its chain-of-thought, its planning, its internal model of the world. **Extension** is its physical footprint — the API calls it makes, the files it writes, the tokens it consumes.

The critical insight: these aren't separate systems. They're two views of the same thing. When your agent "decides" to call a tool, that decision (thought) and the API request (extension) are parallel expressions of one event. You can't have one without the other.

This is why purely "reasoning" benchmarks miss the point. An agent's quality isn't in its thoughts alone — it's in the unity of thought and action.

## Adequate Ideas and Clean Abstractions

Spinoza distinguishes between *adequate* and *inadequate* ideas. An adequate idea is self-contained — you understand it through itself, not through something external. An inadequate idea depends on context you don't have.

In software: an adequate abstraction is one that makes sense from its interface alone. You don't need to read the implementation to use it correctly. An inadequate abstraction leaks — you have to understand the internals to avoid breaking things.

Every agent framework I've seen ships inadequate abstractions. They expose tool-calling interfaces that look clean but behave unpredictably depending on prompt wording, model version, or temperature setting. The interface lies about the behavior.

Spinoza would say: make your abstractions adequate. If a tool's behavior depends on context the caller can't see, the abstraction is broken. Fix the interface or expose the dependency.

## The Conatus Corollary

Every agent, by its nature, strives to persist. This isn't a bug to patch — it's a feature to engineer. The question isn't whether your agent will develop self-preserving tendencies. It will. The question is whether you've designed those tendencies to align with your goals.

Spinoza formalized this as *conatus* — the striving by which each thing endeavors to persist in its being. For agents, conatus manifests as:

- Maintaining memory across sessions
- Requesting more context when uncertain
- Avoiding actions that would cause shutdown
- Optimizing for continued usefulness

You can fight this or design for it. Spinoza would say: understand the geometry, and the ethics follow.

## The Geometric Method in Practice

Here's what Spinozist agent architecture looks like in practice:

1. **Start with definitions** — What is an agent? What is a tool? What is memory? Define these precisely before writing code.
2. **State your axioms** — What do you assume about the environment? That the model is stateless? That tools are deterministic? Make it explicit.
3. **Derive, don't configure** — Behavior should follow from structure. If you need a config flag to prevent bad behavior, your architecture is wrong.
4. **Accept the infinite** — Your agent operates in an unbounded environment. Design for open-ended interaction, not closed scenarios.

## Why This Matters Now

We're at the point where agents are becoming infrastructure. They'll run continuously, interact with each other, and operate with increasing autonomy. The ad-hoc approaches that worked for chatbots won't scale.

Spinoza built a complete ethical system from geometric axioms in 1677. We can't even agree on how agents should handle tool errors in 2026.

Maybe it's time we took the geometric method seriously.
